# Enterprise Document AI

**Private, browser-native RAG (Retrieval-Augmented Generation).** Upload PDFs, ask questions, and get answers with page-level citations. PDF parsing, embeddings, retrieval, and LLM inference all run locally in your browser, with no backend and no API keys.

**[Live demo](https://venantiuscyra4.github.io/enterprise-document-ai/)** · Requires Chrome or Edge with WebGPU for the answer-generation step.

> Built for learning and portfolio purposes. Not production-ready (see [Known limitations](#known-limitations)).

---

## Try it live

**Test it here: [https://venantiuscyra4.github.io/enterprise-document-ai/](https://venantiuscyra4.github.io/enterprise-document-ai/)**

1. Open the link in **Chrome or Edge** (WebGPU is needed to generate answers).
2. Click **+ Upload PDF** and choose a text-based PDF. To try it quickly, use the sample handbook in [`/tests`](tests) (`Northwind_Employee_Handbook.pdf`).
3. Wait for the chunks to be embedded (a progress bar is shown).
4. Ask a question. If you use the sample handbook, try:
   - *How many days of earned leave do employees get each year?*
   - *What is the hotel limit per night in Mumbai?*
   - *How quickly must a lost laptop be reported?*
   - *Summarize this document.*
5. Click **Sources** to see the retrieved chunks, pages and similarity scores.

The first answer takes longer because the browser downloads and caches the embedding and language models. Your PDFs never leave your device.

## Features

- Upload and manage multiple PDFs (stored locally in the browser with IndexedDB)
- Semantic search over document chunks using cosine similarity
- Answers generated by a small LLM running on-device via WebGPU
- Page-level citations for each answer
- Support for broad requests ("summarize this document") as well as specific questions
- A configurable retrieval threshold (cosine similarity ≥ 0.30)
- Static deployment on GitHub Pages: no server, no API key, no paid LLM API

## How it works

```
PDF  ->  extract text per page  ->  sentence-aware chunks (~800 chars, 120 overlap)
     ->  embed chunks (all-MiniLM-L6-v2, 384-dim)  ->  store in IndexedDB

Question  ->  embed question  ->  cosine similarity vs. all chunks
          ->  keep top candidates above threshold (>= 0.30), remove near-duplicates, take up to 4
          ->  build prompt with the retrieved chunks  ->  SmolLM2 via WebLLM (WebGPU)
          ->  answer + page citations
```

**Workflow**

1. **Upload:** PDFs are processed entirely in the browser. There is no document-processing server.
2. **Text extraction:** PDF.js extracts the text page by page and keeps page numbers for later citations.
3. **Chunking:** Text is split into sentence-aware chunks of roughly 800 characters, with about 120 characters of overlap between neighbors.
4. **Embedding:** A lightweight MiniLM model (`all-MiniLM-L6-v2`), run through Transformers.js with WebAssembly, converts chunks and questions into 384-dimensional vectors.
5. **Storage:** Chunks, vectors and metadata are saved locally in IndexedDB.
6. **Retrieval:** The question's vector is compared with every chunk vector using cosine similarity. The top 10 candidates are kept, near-duplicate chunks are removed, and chunks scoring below the 0.30 threshold are dropped. Up to 4 chunks are passed on. For broad requests ("summarize this document"), the best chunk from each page is used instead (up to 12).
7. **Threshold check:** If no chunk passes the threshold, the app answers "The information is not available in the provided document." without calling the model. Otherwise the retrieved chunks go into the prompt, which also instructs the model to decline when the sources do not contain the answer. (This check is weak on questions from the same topic area as the document. See [Known limitations](#known-limitations).)
8. **Generation:** A small local model (`SmolLM2-360M-Instruct`) runs through WebLLM on WebGPU and answers from the retrieved text.
9. **Citations:** The answer references the page numbers of the source chunks.

The design goals are privacy, no paid LLM APIs, no remote vector database, and simple static hosting.

## Tech stack

| Component | Technology |
|---|---|
| Framework | Next.js (static export), React |
| Language | JavaScript |
| Styling | Tailwind CSS |
| PDF parsing | PDF.js (`pdfjs-dist`) |
| Embeddings | Transformers.js (`@huggingface/transformers`), `Xenova/all-MiniLM-L6-v2` (384-dim, WASM, q8) |
| LLM runtime | WebLLM (`@mlc-ai/web-llm`) with WebGPU |
| LLM | `SmolLM2-360M-Instruct-q4f32_1-MLC` |
| Storage | IndexedDB (browser-local, no remote vector database) |
| CI/CD and hosting | GitHub Actions, GitHub Pages |

Note: your documents stay on your device, but the embedding and LLM model files are downloaded from the internet the first time you use the app and then cached by the browser.

## Getting started

**Requirements:** Node.js 24.x, npm 11.x, and Chrome or Edge on WebGPU-capable hardware (needed for LLM inference).

```bash
git clone https://github.com/venantiuscyra4/enterprise-document-ai.git
cd enterprise-document-ai
npm install
npm run dev
```

Open http://localhost:3000, upload a PDF, wait for embedding to finish, then ask a question.

Production build (static export to `out/`):

```bash
npm run build
```

## Evaluation

The system was tested on a small benchmark I wrote: a 5-page fictional company handbook (HR, leave, expenses, IT security, learning) and **22 questions**, with the expected answer and page recorded for each.

- **18 answerable questions:** fact lookups, multi-part questions, and simple reasoning
- **4 unanswerable questions:** topics the handbook never mentions (the app should decline)

| Metric | Result |
|---|---|
| Answer accuracy (answerable questions) | **78%** (14 of 18) |
| Citation accuracy (correct page cited) | **89%** (16 of 18) |
| Refusal accuracy (unanswerable questions) | **25%** (1 of 4) |

The test PDF, the questions with expected answers, and a scoring sheet are in the [`/tests`](tests) folder so the results can be reproduced.

**How to read these numbers:** this is a small, hand-written test set and a small 360M-parameter model, so treat the results as an indication of behavior and not a formal benchmark. The weak spot is refusal.

## Known limitations

- **Out-of-document questions:** the small model often answers questions that are not in the document instead of declining (refusal accuracy was 25%). A similarity threshold alone does not catch questions from the same domain as the document, because unrelated chunks can still score above 0.30.
- **Small model:** a 360M-parameter model can miss details or merge facts, especially on multi-part questions.
- **WebGPU required** for answer generation, so Chrome or Edge on supported hardware. Retrieval and citations work without it.
- **Text PDFs only:** scanned or image-only PDFs are not supported (no OCR).
- **Evaluation scale:** one fictional document and 22 questions. It does not yet cover long documents, tables, or multi-document questions.
- **First load is slow:** model files are downloaded and cached on first use.
